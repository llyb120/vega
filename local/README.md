# vega-local

Run the updated client and sign in to Vega **once on that computer**. The desktop webpage posts a one-use, 15-second ticket to `http://127.0.0.1:47673/agent`, which answers with one event stream (`text/event-stream`). After you approve the local site permission, the native client exchanges that ticket directly with the backend for a revocable device credential. The credential never enters the webpage.

After pairing, the client connects directly to `/api/local-agent/socket` with its device credential. The website shows **waiting for site permission → verifying login → connecting to backend**, and only confirms success after the native backend sends `ready`. Failures show a sanitized stage/reason and HTTP status (when available), with **重新检测** for a fresh handshake. No token, upstream response body or jobs are relayed through this diagnostic channel. An old client that cannot confirm backend readiness prompts you to upgrade.

**You may close the webpage, let the browser sleep, or use Vega from a phone.** As long as the computer, client and network remain available, it stays usable. Client and server restarts reconnect automatically without a new website login; network reconnects never replay jobs. Both HTTP/WS and HTTPS/WSS origins are supported, including remote HTTP sites. HTTP sends website logins, device credentials and commands in plaintext and permits network tampering; HTTPS remains recommended, but is not required. HTTPS certificates are still verified.

The website lists available clients by computer name, platform and short device ID, scoped to the current account. Heartbeats tolerate 30 seconds of silence. A closed native socket or missed heartbeats starts a 60-second recovery window instead of immediately failing work; the selected client remains reserved while new operations wait for reconnection. Only expiration of that window marks it offline. Phones/tablets do not connect to a loopback client; they select an authorized computer through the server.

There is no per-employee Master/Follower configuration. A new task binds its workspace to the cloud by default; an in-flight task keeps its execution node. To use a client, pause the running task, choose an online client in its task details and select **交接**; resume a paused task explicitly afterwards. A task that has already started copies eligible workspace files to the client's working directory, keeps both sides of conflicts, and refuses oversized workspaces (2000 files, 4 MiB per file, 16 MiB total). The client process is online while it is running; when it exits, its work resumes from a restore point on the remaining side.

Files are not continuously synchronized across nodes; an explicit handoff copies eligible workspace files and does not delete local files. `read`, `write`, `edit`, `bash`, directory changes and the `chrome` tool run on whichever node currently holds the task's workspace; `sqlite:` archives and skill storage remain server-side.

The bundled **Vega Chrome** extension is embedded in the native client and belongs to Vega alone: its own manifest `key` (extension ID) and its own loopback ports `47753–47762`, so Nova's extension (`47653–47662`) and this one never discover or attach to each other. The client always unpacks it to `<data>/extension/vega-chrome` itself; the default 无头浏览器 loads it from there automatically. Only **用我自己开的 Chrome** needs it in your own browser: **连接授权 → 授权 → 更新浏览器扩展** unpacks the same folder and asks a 牛马 to load it in this computer's Chrome through `appuse` in a computer session, or you can load it by hand in `chrome://extensions`. The button only works while this machine's client is online and an available 牛马 exists. The existing Chrome tool (including screenshots, DOM, DevTools and uploads) uses that computer's browser/login state and validates upload paths on that computer. The native client grants an exclusive lease to one session for its entire active turn, across users and server connections; competing sessions pause without input and can continue after the holder finishes or is stopped. A brief native backend disconnect preserves its lease during recovery; an expired recovery window or revoked connection releases it. A missing extension, an old/offline client or a busy browser never falls back to the server or another computer. Administrator server-browser management pages remain separate from the conversation's browser tool.

Short network outages preserve the execution instance and pending work. After reconnection, the client retransmits only unacknowledged **results**, never operation inputs; the same turn continues automatically. A response timeout also gets one reconnect attempt to collect its cached result before pausing. If recovery expires, the client process restarts, or a result remains uncertain, work pauses so you can inspect the actual result, repair the connection and explicitly continue. No command is replayed or silently rerun on another device or the server. Cancelling a session cancels pending shell processes immediately when connected, or reconciles cancellations on reconnection; an outage lasting beyond the recovery window also cancels them locally. Closing the webpage does **not** disconnect the native client or cancel its work. Older servers/clients retain the safe pause behavior but require a coordinated upgrade for in-flight recovery.

Browser interaction is **extension-only** and always drives this computer's Chrome, never the server's. The **browser mode** in **连接授权 → 浏览器** decides which Chrome:

- **无头浏览器（默认）**: the client starts its **own hidden Chrome** (its own profile under the client's data directory, copied cookies/Local State from this computer's Chrome on first start), loads the bundled extension into it over CDP, and reclaims it after 15 idle minutes (never while a session still holds the browser). Nothing to install by hand, no window opens, and your own browser windows and tabs are never touched. The profile is persistent, so logins inside it survive restarts. `VEGA_CHROME_PATH` names the binary when Chrome is not in a standard location (on Linux/macOS it is the only way to pick a specific Chromium). Chrome locks its Cookies database while it runs, so that first-start copy usually finds nothing; the client then syncs login state through the extension **both ways** — your Chrome's cookies into the headless profile, and a site you logged into inside the headless browser back into your own Chrome. Each direction only fills what the other side lacks (or replaces a cookie that has expired), so a live session on either side is never overwritten by a stale copy; only one browser is synced (Google Chrome first), so several profiles or accounts never receive each other's logins. Writing back needs no extra window or tab: the client attaches to one background tab, writes, and detaches. A login you remove in your own Chrome is not put back, and a finished turn only touches your Chrome when the headless browser really gained a new login. This needs the Vega Chrome extension in your own Chrome (**连接授权 → 授权 → 更新浏览器扩展**; only the extension paired in this computer's Chrome counts), and only cookies move — no localStorage, IndexedDB or passwords, no oversized values and no partitioned (CHIPS) cookies. Your Chrome must have a background tab (the active one does not count); the client detaches right after, opens no window, and skips the sync while a session holds the local browser. At most once per 10 minutes per headless instance, again when a browser turn ends and on each new start; the result shows in the 浏览器 card and `client.log` without the cookie contents.
- **用我自己开的 Chrome**: the client routes browser operations to the Chrome you opened yourself, which must have the extension loaded (see below). Use it when a site only works with your normal profile or when you want to watch and take over.

An operation never silently falls back to the other mode or to the server: if the selected Chrome cannot be reached, the step reports it as unavailable.

The client listens on the first free loopback port in `47753–47762`; the extension pairs through `/pair`, authenticates `/poll` and `/reply` with that process's token, and executes CDP through `chrome.debugger`. Chrome does not need a `9222` remote-debugging listener. Multiple Chrome/Edge profiles can stay connected, with per-client queues, Chrome preferred for new turns, 20-second polls and the same 3-second ordinary / 10-second CDP deadlines as Nova. An acquired turn remains pinned to its browser and never silently switches profiles. Employee main tasks must use `employee.relay(scene=computer)` to reach the browser tool; a missing `chrome` tool or a failed `9222` probe is not evidence of extension failure. If the extension cannot proceed or a native dialog requires input, the assistant must stop and ask you to handle it, never fall back to desktop automation. Computer scenes retain `bash` for ordinary file, build, test and diagnostic commands. Command execution on both the server and native client rejects recognized native mouse/keyboard/focus APIs, UI automation tools, alternative browser drivers and encoded PowerShell commands before dispatch or process creation. This is a conservative literal-command guard, **not an OS sandbox**: it can also reject diagnostic text containing these names (use `read` instead), and cannot inspect arbitrary saved scripts or executables. Rebuild/restart the native client and upgrade the server for both checks to take effect.

## 桌面客户端窗口 (Windows)

The client UI is a real desktop **window**, not a popover bubble beside the taskbar: tray → **客户端** (or the taskbar butterfly) opens a Go-created window hosting the embedded page from `local/ui/` (index.html / style.css / app.js / bot-avatar.js, all served by this process under `/assistant/<token>/`), 1040×760, with remembered size and position. It has **no system title bar** — the title bar, the 会话 rail, the message stream and the rounded input capsule are drawn in the page; dragging, minimizing, maximizing and closing are sent back to the host through `chrome.webview.postMessage`, because the whole client area is the page (`WM_NCCALCSIZE` returns 0). Closing hides the window off-screen instead of quitting: the process and the loaded page stay warm, and the next click reopens it. The account pill at the bottom of the rail opens 设置 — the local permission page described below. The window runs in its own child process (`vega-local --desktop <url>`), so a failed WebView2 initialisation only takes down that window, never the tray or in-flight jobs. The **hint bubbles** above the butterfly (正在操作这台电脑 / 需要你核对) still appear before desktop input and after an uncertain result; they can be turned off in 设置 → 电脑 along with the butterfly itself.

## Device credentials and revocation

Open **连接授权** from the Windows tray to manage trusted sites, **浏览器** mode (无头 / 用我自己开的 Chrome), and **补充内容**. There is no separate native text dialog, and no switches for login-state borrow, local SSH keys, traffic relay, going offline, or per-employee Master/Follower. Login-state borrow, git-over-SSH use of this computer's `~/.ssh`, and one-way network borrow (cloud → this client) are always allowed; a client never borrows the server's network or receives another computer's traffic. **授权 → 浏览器扩展 → 更新浏览器扩展** unpacks the bundled **Vega Chrome** extension into this client's data directory and asks a 牛马 to load it in this computer's Chrome through `appuse`; it only works while this computer's client is online. The supplement is a multiline field; Save persists it and updates paired backends without restarting or interrupting jobs, and saving an empty field clears it. Only sessions bound to this client receive the hints; listing project directories does not switch their working directory or grant permission. The content is shared with this client's authorized Vega sites, so do not enter passwords or keys. The limit is 8192 UTF-8 bytes. Other platforms can use the same local permission-page URL (printed when the client starts), without a tray.

The per-user config directory contains `vega-local/trusted-sites.json`: the stable device ID, trusted origins and paired credentials. Windows protects tokens with current-user DPAPI; Unix stores them in a mode-0600 file under the user's config directory. The server stores only token hashes, bound to one account/device; these tokens cannot log into the website or call general APIs. No website password or login cookie is stored by the client.

Windows tray → **连接授权** can revoke a trusted site: it removes its local credentials and stops its native connections. Account password/role changes and disabling access revoke the backend's device credentials too. A logged-in user can revoke one of their own devices with `POST /api/local-agent/revoke` and `{clientId}` (normal cookie/CSRF protection). Revoked clients require a fresh website handshake; repeated authorization while a healthy token exists reuses it without interrupting work. Website logout and the 7-day website cookie expiry do not revoke an independently authorized device.

Upgrade the server, webpage and native binary together for the initial installation of automatic updates (client **0.3.0**). Client **0.4.5** gives the Windows binary an embedded application manifest (supportedOS through Windows 10/11 plus per-monitor-v2 DPI): without it the taskbar Butterfly's layered child window gets no surface on Windows 11 and never appears, and the process starts as a 96-DPI virtualized app. `local/vega-local.rc` and `local/vega-local.manifest` are the sources; `rsrc_windows_amd64.syso` is generated and committed so the Docker/CI cross build still needs no Windows toolchain — regenerate it with `windres -i vega-local.rc --input-format=rc --output-format=coff -o rsrc_windows_amd64.syso` (mingw-w64) after editing either file. Client **0.3.1** posts results larger than 256 KB to `POST /api/local-agent/result` (device token + `X-Vega-Instance`) instead of the socket, so a large file read never stalls heartbeats; the server now refuses socket messages over 1 MB, so 0.3.0 clients pick up 0.3.1 through the automatic update the next time they are idle. Client **0.3.2** adds the `key` job: an employee's vault SSH private key is written as a mode-0600 file under `<temp>/vega-keys` for one run, removed when the run ends, and the directory is cleared when the client starts; older clients refuse SSH key entries with an update prompt. Existing older binaries cannot update themselves; replace and start that binary once. Later releases download and restart silently as described below. The permission page confirms that the site permission was saved and directs you back to the website for the backend result. Revoking permission while the website is open will trigger a new authorization request on its next detection attempt; close that page to stop requesting. Old webpage job relays are no longer used. Existing stable device IDs and trusted origins are preserved; open the desktop website once after upgrading to obtain a device credential. Historical sessions without a device binding still require choosing a device once.

Reverse proxies must stream Server-Sent Events without buffering (`proxy_buffering off`, no response buffering at the CDN) and forward the Authorization header for `/api/local-agent/socket` and `/api/local-agent/relay` (also forward `X-Vega-Relay`), in addition to `/api/events` and `/api/chrome/live`; these four keep one long GET open, so raise the proxy read timeout above the 15-second keepalive interval. There is no WebSocket Upgrade to forward. Allow request bodies of at least 48 MiB for `POST /api/local-agent/result` (nginx `client_max_body_size`), keep the client's paired Origin on the same scheme/host the upload uses (no HTTP→HTTPS redirect for that POST), and do not inject a browser `Origin` header on native client requests. No extra public port is needed; never expose the client's loopback port.

## Account network relay (client 0.3.3)

Hosts the server cannot reach may be bridged one-way through this computer for the owning account. There is no traffic-relay switch or hostname list, and no Master requirement — any online authorized client of the account can carry it. A client never uses the cloud as egress. Multiple clients claiming the same hostname fail closed. The **账户** tab is only for removing a paired account. Upgrade the server and native client together; no prebuilt binaries are changed by a source-only build.

Every server-side employee browser uses its owner's loopback SOCKS5 gateway. Matching hosts go through that account's approved client with DNS resolved there; an unapproved port, offline client or several clients claiming the same hostname fails closed and never falls back to direct access. Unmatched hosts dial from the server first, and a failure (or five seconds without connecting) is retried once through that account's active client whenever its relay switch is on — no rule needed — so hosts only the user's computer can reach still work; the reverse never happens. A host that worked through the client is remembered for ten minutes, so the next connection to it skips the failed direct dial; a tunnel that dies before it is ready, or a changed relay switch, drops that memory and the next connection probes again. Saved rules survive server restarts and credential revocation to prevent accidental public fallback; reconnect/reauthorize the original client and clear its rules explicitly to remove a stale policy. Changes flush that account's pooled browser connections, so save while idle. The relay never replays requests after disconnection. A `bash` command that runs on the server also gets it as proxy variables for the same account whenever an enabled client is online: `ALL_PROXY` (HTTPS git, curl), `GIT_SSH_COMMAND` (git over SSH) and `VEGA_PROXY_COMMAND` for a plain `ssh -o "ProxyCommand=$VEGA_PROXY_COMMAND" host`; commands that run on the native client are unaffected. Each tunnel is TCP only and closes after five minutes without traffic, so an idle SSH session needs keepalives.

Each TCP connection uses its own authenticated transport: one ordered event stream downstream and one small POST per frame upstream (frames are base64, so tunnel order can never be reordered), with bounded acknowledged frames, timeouts and connection limits; it does not occupy task RPC slots. Revocation/control-channel loss closes tunnels. Client DNS results are checked before dialing the resolved IP; loopback, link-local/metadata and multicast targets are blocked, while private intranet addresses are permitted. This is TCP web access, not a VPN: UDP/QUIC is disabled and non-proxied WebRTC UDP is restricted in employee browsers. Only the browser's own authenticated control bridge bypasses the proxy.

Use HTTPS for the Vega site: an HTTP deployment exposes credentials and unencrypted payloads to the network. HTTPS target traffic remains end-to-end TLS without interception; enterprise certificates must be trusted in the server browser. Cookies, device/client certificates and integrated OS login state are not copied from the native computer. Website content reaches the server browser and task processing. The loopback proxy assumes other processes on the server host are trusted; it is not a sandbox against hostile host processes.

## Automatic updates

`local/VERSION` is the native client's independent `major.minor.patch` version; increment it for each client release. On connection to an update-capable server, the client checks that deployment's `/clients/manifest.json` in the background, then hourly (failed checks retry after five minutes). Only higher versions for the current OS/architecture are downloaded; exact size and SHA-256 must match. Downloads do not interrupt jobs. Automatic executable downloads require **HTTPS**, except loopback HTTP for development; remote HTTP connections still work but cannot auto-update. Redirects to another origin are refused.

Installation requires **no running session that uses this client**, across all connected accounts and backends. A session remains busy throughout model thinking, streaming, tool roundtrips and Fire phase transitions, including employee sessions; a gap between local commands is **not** idle. The client also waits for 60 seconds without jobs or unacknowledged results, with no active browser lease. Session activity is synchronized on connection and heartbeats and rechecked atomically by the backend before reserving an update; a busy rejection keeps that session's socket connected. Every paired backend must be connected and support automatic updates. Each backend then atomically reserves the existing execution instance, so operations arriving during the restart wait for reconnection instead of failing or being replayed. The updater preserves the working directory, stable device ID, credentials and execution instances, replaces the executable in its original directory, and launches the new client with no dialog or console window. A startup check must pass before the backup is removed; failure restores and starts the old binary. That process skips the failed release until a higher version is published (a manual restart permits another attempt), preventing an automatic restart loop. An unwritable installation stays on the old version. The computer must remain powered on and the deployment must serve matching binaries and manifest; rollback is a startup check, not a guarantee against later runtime bugs.

## Build

Docker builds all five clients from the same source as the server: Windows x64 (tray), Linux x64/ARM64 and macOS Intel/Apple Silicon (headless). After deploying the image, sign in and open **资源 → 客户端下载**; files are served by that deployment at `/clients/`, not fetched from an external release. The Go toolchain is only in the build stage, not the runtime image.

For non-Docker deployments, build the matching binaries below and place them in `web/public/clients/` using the filenames `vega-local-windows-amd64.exe`, `vega-local-linux-amd64`, `vega-local-linux-arm64`, `vega-local-darwin-amd64` and `vega-local-darwin-arm64`. Run `node scripts/client-manifest.mjs web/public/clients` from the repository root **before** `npm run build`. Publish the manifest and all five binaries together. Docker does this automatically; CI includes the manifest in its release assets. A plain frontend/server build does not compile the clients. Check the installed version with `vega-local --version`.

Windows (system tray only, no console window):

```powershell
go test ./...
go build -ldflags="-H=windowsgui" -o vega-local.exe .
```
Use the rebuilt `.exe`, not an older download or `go run .`. Windows detaches the client from any console at startup without closing the parent terminal, and shell commands use `CREATE_NO_WINDOW`. A plain console-mode build may still flash before startup; the GUI build avoids that entirely.

CI builds Windows tray and Linux/macOS headless binaries. Linux/macOS use `go build -o vega-local .` and require a browser only for first-time authorization; when automatic opening is unavailable, the client prints the local permission-page address.
